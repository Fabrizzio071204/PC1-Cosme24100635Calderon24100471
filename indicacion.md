Desarrollo de Aplicaciones Móviles — Desan UniversityProyecto: Travel Companion AppConsideraciones GeneralesNombre del Proyecto: Estará conformado por la siguiente estructura: PC01MOVILESAPELLIDOPATERNO1CODIGO1APELLIDOPATERNO2CODIGO2.  Modalidad: La práctica será desarrollada en pares.  Flujo de Trabajo en Git:Cada integrante debe trabajar obligatoriamente en una rama independiente utilizando la nomenclatura feature/nombre-funcionalidad.  No está permitido trabajar directamente sobre main o master.  Cada integrante debe realizar al menos tres commits propios.  Cada funcionalidad desarrollada deberá integrarse mediante Pull Request (PR).  El estudiante que crea el Pull Request NO podrá aprobar ni fusionar su propio PR. La revisión, aprobación y fusión deberá ser realizada por su compañero.  Se verificará rigurosamente el historial de commits, ramas, Pull Requests y autores.  Evaluación y Sustentación:El docente podrá solicitar explicación del código, modificaciones menores o justificación de decisiones técnicas.  Si un integrante no puede explicar una funcionalidad desarrollada bajo su autoría, el puntaje asociado podrá ser descontado.  El uso de IA está permitido como apoyo, pero no reemplaza el análisis ni la sustentación.  Entrega: El proyecto deberá publicarse en GitHub como repositorio público. No será necesario enviar el código fuente; bastará con proporcionar la URL del repositorio.  Estructura de PantallasPantalla 0: Menú Principal de Navegación (2 Puntos)Componentes a utilizar: Scaffold, Column, Button, Navigation Compose.  Objetivo: Debe permitir navegar a las siguientes secciones:  Calculadora de Equipaje.  Planificador de Presupuesto de Viaje.  Catálogo de Destinos Turísticos.  Permiso de Ubicación para Asistencia de Viaje.  Pantalla 1: Calculadora de Equipaje (3 Puntos)Componentes a utilizar: Column, OutlinedTextField, RadioButton o DropdownMenu, Button, Text.  Datos de entrada:Peso de la maleta.  Tipo de vuelo.  Tipos de vuelo y restricciones:Nacional: máximo 23 kg.  Internacional: máximo 32 kg.  Resultados a mostrar:Si cumple el límite permitido.  Si excede el límite permitido.  Cantidad de kg excedidos.  Validaciones requeridas: Campo obligatorio, valor numérico y mayor a cero.  Pantalla 2: Planificador de Presupuesto de Viaje (4 Puntos)Componentes a utilizar: Column, OutlinedTextField, DropdownMenu, Button, Text.  Datos de entrada:Cantidad de días.  Presupuesto diario.  Tipo de alojamiento.  Tipos de alojamiento y factores:Económico (factor: 0.8).  Estándar (factor: 1.0).  Premium (factor: 1.5).  Lógica de cálculo:Fórmula: $\text{Total} = \text{días} \times \text{presupuesto diario} \times \text{factor}$.  Resultados a mostrar:Presupuesto total (con dos decimales).  Mensaje descriptivo del escenario calculado.  Validaciones requeridas: Campos obligatorios, días mayores a cero y presupuesto mayor a cero.  Pantalla 3: Catálogo de Destinos Turísticos (5 Puntos)Componentes a utilizar: LazyColumn, Card, Row, Column, AsyncImage (Coil), Text.  Requisitos técnicos:Crear un Data Class llamado Destination.  Utilizar una lista simulada con al menos cinco destinos.  Estructura del objeto / Elementos del Card:Imagen (vía URL).  País.  Ciudad.  Costo promedio.  Resumen (al final del listado):Cantidad total de destinos.  Suma acumulada de los costos.  Pantalla 4: Permiso de Ubicación para Asistencia de Viaje (2 Puntos)Componentes a utilizar: Column, Text, Button.  Requisitos técnicos:Implementar permisos en tiempo de ejecución mediante ActivityResultAPI y rememberLauncherForActivityResult.  Permisos a solicitar: ACCESS_FINE_LOCATION y ACCESS_COARSE_LOCATION.  Estados a mostrar en pantalla:Permiso concedido.  Permiso denegado.  Permiso pendiente de solicitud.  Nota: No es necesario obtener la ubicación real del dispositivo.  Rúbrica de Git y Trabajo Colaborativo (4 Puntos)Para obtener el puntaje completo en este criterio se verificará que:  Ambos integrantes trabajen en sus respectivas ramas feature/*.  Ambos integrantes realicen commits propios.  El historial de Git evidencie la participación equitativa de ambos estudiantes.  Existen Pull Requests creados, revisados, aprobados y fusionados por el compañero correspondiente.  El equipo sea capaz de explicar correctamente todos los cambios realizados.
